ACTIVE DIRECTORY · OPERATIONS

Active Directory replication preflight for provisioning projects.

Practical checks I use before HR-driven provisioning or other large identity changes, with emphasis on separating directory-health problems from provisioning problems.

WHY IT MATTERS

Replication failures create “ghost” provisioning symptoms.

If users are created or modified while domain-controller replication is unhealthy, the resulting symptoms can look like connector instability:

  • User exists on one DC but not another.
  • Group membership differs by DC.
  • Password or authentication behavior changes depending on which DC answers.
Operational rule: if replication health is red, pause the provisioning rollout and fix AD first.

FAST CHECKS

Run before and after high-impact identity changes.

1. Replication summary

repadmin /replsummary

Use this first for a quick view of failure counts and replication health across domain controllers.

2. Per-DC inbound replication

repadmin /showrepl *

Useful when the summary indicates failures and you need to identify the affected DC or naming context.

3. Domain-controller diagnostics

dcdiag /e /c /v

Broader forest/domain-controller diagnostics when replication symptoms may be tied to DNS, services or other DC health conditions.

Interpretation

I compare the pre-change and post-change state. If replication health changes, I address the directory condition before spending time in provisioning logs.

COMMON ROOT CAUSES

Start with the dependencies AD replication actually relies on.

DNS

Incorrect DNS configuration, stale records, or configuration left behind after a DC rebuild/replacement.

Time

Clock skew and NTP hierarchy issues that also affect Kerberos and authentication behavior.

Sites & links

Site-link schedules or topology that no longer match the real network path.

Network / firewall

Inter-site filtering or connectivity that blocks required replication traffic.
