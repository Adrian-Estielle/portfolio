WORKDAY · MICROSOFT ENTRA ID · IDENTITY

Workday → Microsoft Entra ID inbound provisioning.

A practical runbook for the Workday-to-Entra provisioning pattern: source permissions, stable identity matching, scope, attribute mapping, pilot testing, logs, and the failure modes worth checking first.

ARCHITECTURE

Keep source, transformation, matching, and target behavior distinct.

Workday (HR)  -- WWS / SOAP -->  Entra Provisioning Service  -->  Entra ID Users

Source

Workday worker data. Which fields are available depends on the security domains granted to the integration user.

Transform

Attribute mappings, expressions, formatting rules and fallbacks applied by the provisioning configuration.

Match

A stable anchor such as EmployeeID / WorkerID used to associate the source worker with the correct Entra identity.

Target

Entra user creation and updates, with provisioning logs showing the action, result and correlation information.

DESIGN FIRST

Make the identity decisions before configuring the connector.

Identity anchor

  • Choose one durable match key, typically EmployeeID or WorkerID.
  • Decide how rehires and name changes should behave.
  • Define whether UPN is email-based or independently generated.
Failure mode: a bad match key can “succeed” by creating duplicate identities rather than producing an obvious connector error.

Scope

  • Start with a pilot population rather than broad tenant scope.
  • Use assigned users/groups or a narrow filter during validation where appropriate.
  • Treat expansion from pilot to production scope as an explicit change.

WORKDAY

Configure a non-interactive integration identity with least-required access.

1. Integration System User (ISU)

  1. Workday search → Create Integration System User.
  2. Set the integration username and credential.
  3. Set session timeout appropriately for integration use; existing implementations commonly use 0.
  4. Disable interactive/UI sessions where supported by policy.

2. Integration security group

  1. Workday search → Create Security Group.
  2. Select Integration System Security Group.
  3. Add the integration user to the group according to the tenant's security model.

3. Domain permissions

  1. Use Maintain Permissions for Security Group.
  2. Grant only domains required by the attributes you intend to map.
  3. Activate pending security-policy changes.

Field check

If a mapped value such as work email, manager, department, location or phone arrives blank, verify the Workday integration account can actually read the corresponding source node before changing Entra mapping logic.

ENTRA CONFIGURATION

Build the gallery application, test source connectivity, then work on mappings.

Create the enterprise application

  1. Microsoft Entra admin center → Enterprise applications.
  2. Select New application.
  3. Choose the Workday-to-Microsoft-Entra user-provisioning gallery application.

Configure provisioning

  1. Open the application → Provisioning.
  2. Set provisioning mode to Automatic.
  3. Enter the Workday WWS endpoint and integration-user credentials.
  4. Run Test Connection.
If source authentication/connectivity fails, fix that before touching mappings; otherwise mapping changes only add noise.

MAPPINGS & MATCHING

Design the identity relationship so the same person remains the same object.

  1. Provisioning → Mappings → open the primary Workday-worker-to-Entra-user mapping.
  2. Confirm the source attribute used as the matching key.
  3. Confirm the target attribute used for matching.
  4. Review UPN/email-generation rules and collision behavior.
  5. Review required vs optional source attributes and any expression/fallback logic.

PILOT & VALIDATION

Use one worker to prove the path before enabling continuous scope.

Provision on demand

  1. Keep the application scoped to the pilot population.
  2. Provisioning → Provision on demand.
  3. Select a representative pilot worker.
  4. Run the provision and inspect the evaluated mapping/actions.

Validate the target

  • UPN / email / display name
  • employee identifier / matching attribute
  • manager relationship if mapped
  • department / location / organization data
  • expected create-vs-update behavior

Only after the on-demand path is correct should continuous provisioning be enabled for the intended scope.

LOGS

Use the provisioning record as the first source of truth.

Entra admin center → Enterprise applications → Workday provisioning application → Provisioning logs.

Fields I look at first:

  • Action — create, update, skip or other evaluated operation.
  • Status — success or failure.
  • Failure reason — what the provisioning service reports rather than what the user observed.
  • Correlation ID — useful for tracing one attempt end-to-end.
Example sanitized log fields
Status: Success
Action: Create
Source system: Workday
Target system: Microsoft Entra ID
Target object: user <REDACTED_GUID>
Start time / End time
Correlation ID: <REDACTED_CORRELATION_ID>

COMMON FAILURE MODES

Check the structural causes before treating the connector as random.

Workday permissions

The ISU cannot read a field that the mapping expects, so the source value is absent or incomplete.

Source endpoint / auth

Wrong Workday URL, credential or source connectivity produces broad failures before mapping logic matters.

Match-key drift

A worker that should update an existing identity is interpreted as a new person because the matching anchor changed or was not stable.

Scope too broad

A configuration issue affects many identities before the pilot path has been proven.
