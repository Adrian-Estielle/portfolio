AZURE · DATA · MIGRATION

3+ TB accounting migration where testing changed the architecture.

The important part of this project was not moving files. It was preserving linked spreadsheet and ERP workflows, validating performance before cutover, and changing the design when the first implementation exposed collaboration and latency limitations.

PROBLEM

Large, interdependent accounting data could not be treated like a normal file-copy project.

Data characteristics

More than 3 TB of accounting data included heavily linked Excel workbooks and ERP-related file dependencies. Preserving file paths, embedded references, permissions and modified metadata mattered as much as the raw copy.

Operational constraint

The production migration needed to fit within a weekend cutover window. Discovery, lab testing, path analysis, migration design and performance validation took place before that cutover; the 48-hour figure applies to the production transition window, not the entire project.

FIRST DESIGN

Azure Files with identity-aware SMB access and regional caching.

Storage

Provisioned Azure Storage / large Azure file shares for SMB-oriented access.

Identity

Worked through AD-backed authentication / Kerberos integration and group-based access rather than direct user assignment.

Regional access

Used DFS namespaces and Azure File Sync patterns to reduce the impact of geographic distance for offices.

Automation

Used PowerShell and LinkFixer rules to handle mappings, preserve or repair references, and make validation repeatable.

WHAT TESTING EXPOSED

A technically valid design was not the best operational design.

Latency and collaboration

Testing exposed latency and file-conflict behavior for actively edited working data, particularly where synchronization and file locking patterns did not align cleanly with how accounting staff collaborated.

Link and path behavior

Long paths, embedded workbook references and LinkFixer limitations required additional rules, scripts and validation. The project needed to prove that the business relationships between files survived—not simply that every file had copied.

REVISED ARCHITECTURE

Separate platforms by workload instead of forcing one storage model.

SharePoint Online

Actively collaborated working data moved toward SharePoint where the collaboration model better matched user behavior.

Azure Files

SMB-oriented and mid-tier data remained on Azure Files where file-share semantics were still appropriate.

Azure Blob

Cold/archive data moved to Blob Storage rather than consuming higher-cost or collaboration-focused tiers.

Remote access

The surrounding work also included modernizing remote access with an Azure-hosted VPN solution and reviewing routing/connectivity requirements.

CUTOVER & VALIDATION

The production weekend was the execution phase of a longer engineering process.

Before

Inventory paths and permissions, test copy performance, validate link-handling rules, identify path-length issues, prepare remediation scripts and confirm the cutover could fit the available window.

During

Execute the production migration, apply mapping/link remediation, monitor permissions and service-account access, and resolve unexpected failures without changing the success criteria.

After

Validate permissions, file structure, workbook/formula integrity and representative accounting workflows with stakeholders before considering the migration complete.

Result

The revised tiered design completed without business disruption and left the environment with a clearer separation between collaborative working data, SMB storage and long-term archival storage.

WHAT THIS DEMONSTRATES

Architecture should be allowed to change when evidence says it should.

The strongest outcome from this project was not defending the original design. It was building enough test coverage to recognize its limitations before forcing the business to live with them, then revising the implementation around the actual workload.
